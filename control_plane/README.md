# CHEMFORGE Control — Enterprise administration pilot (v2.0-alpha)

A separate **server-side** administration component for managed schools. **The CHEMFORGE Student Android APK retains its offline-only architecture and does not need a network connection.** This component is not linked to Android for automatic synchronisation; explicit JSON-export import provides a manual bridge.

## Browser administration — v1.7

Start the same server as described below and open **`http://127.0.0.1:8020/control/`**. Enter the institution-issued administrator or teacher credential. The responsive, self-hosted browser interface supports overview metrics, students, assignments, manual backup import, curriculum release metadata, and (administrator only) teacher credentials and audit logs.

- All browser assets are **served from the same FastAPI origin**; there are no third-party CDNs, trackers or external CSS libraries.
- Credentials are held in **volatile tab memory** only; do not use shared/public computers. Log out and close the browser when finished.
- Browser navigation never bypasses server-enforced roles or tenant isolation. Teachers now receive **no classroom access by default**; administrators must grant specific cohorts, and revocations take effect on the API.
- Importing a CHEMFORGE Android backup **does not verify authenticity** or certify marks. The interface shows unverified attempt counts, not educational outcomes.
- The UI rejects credential transmission on non-HTTPS origins (except localhost loopback). For non-local pilots, put the service behind a securely configured HTTPS reverse proxy and obtain a privacy/security review **before handling real student data**.

The new HTML, JS and CSS are in `control_plane/dashboard/`. HTTP security headers include a restrictive CSP, `no-store`, `nosniff`, `X-Frame-Options: DENY` and a no-referrer policy. This is an interim defence, not an independent security audit.

## Delivered

- SQLite-backed isolated institutional tenants. **No HTTP bootstrap endpoint**; an operator provisions each school by CLI.
- 256-bit random, one-time-revealed administrator, teacher and device tokens; SHA-256 hashes stored rather than raw credentials. Teacher scopes and devices can be revoked; device capabilities automatically expire.
- Role- and cohort-enforced roster management, pseudonymous student identities, cohorts, assignments, retention-by-student-erasure, and scoped audit entries.
- Manual import of `CHEMFORGE_ANDROID` JSON backups from enrolled students; tenant and content fingerprint matching, bounded schema, duplicate detection, transactional ingestion, and idempotency.
- Activity counts separate unverified imports from **zero verified examination records**. This platform does **not** authenticate scores, provide official grades or update on-device mastery.
- Institution-scoped version registry for signed-curriculum **metadata** (hashes/revisions). Registration does **not** sign, scientifically review or validate a `.cfpack` file.

## Local development (never bind publicly without HTTPS and an identity-security review)

Requires Python 3.12+, `fastapi`, `pydantic`, `uvicorn`, `pytest`, and `httpx`.

```bash
python -m pip install -r control_plane/requirements.txt 'pytest>=8,<10' 'httpx>=0.27,<1'
python -m control_plane.cli bootstrap --db ./chemforge-control.sqlite --tenant school-demo --admin-label "Institution Admin"
CHEMFORGE_CONTROL_DB=./chemforge-control.sqlite uvicorn control_plane.app:create_app --factory --host 127.0.0.1 --port 8020
python -m pytest -q tests/control_plane
```

The bootstrap command displays the bearer credential once; transfer it securely, **never commit it, log it, or paste it into an unsecured channel**. The service has no interactive login, MFA, password recovery, password reset, SSO, consent workflow, rate limiting, retention scheduler, distributed deployment or production audit review. It is a **pilot API**, not an enterprise production identity system.

### Example request

```bash
export TOKEN='cfcp_TOKEN_FROM_BOOTSTRAP'     # protect shell history/permissions
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8020/v1/me
curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     --data '{"pseudonym":"Student 01","cohort":"U6-A"}' http://127.0.0.1:8020/v1/students
```

To import a student's offline CHEMFORGE record: export JSON using the Android app's document picker, bring that JSON to an authorised teacher computer by an institution-approved secure method, create/select the student's pseudonymous roster ID, then submit that exact JSON to `POST /v1/students/{student_id}/backups` as `application/json`. The service cannot certify that the file was generated by the Android app or hasn't been edited: **all imported marks remain unverified**.

## v1.7 Teacher cohort grants and device upload gateway

New teachers are **default-deny**. An institution admin must grant class access through the Teachers dashboard or `POST /v1/teachers/{actor_id}/cohorts` with JSON `{"cohort":"U6-A"}`. The same administrator can revoke access with `DELETE /v1/teachers/{actor_id}/cohorts/U6-A`. Existing teachers must be granted cohorts after upgrading. Data are not migrated or deleted.

The Devices tab can issue an expiring credential for a selected student and revoke it later. `POST /v1/devices` takes `{ "student_id": "<registered-roster-UUID>", "label": "School tablet", "valid_days": 7 }` (1–90 days) and returns an ephemeral `cfsync_…` token exactly once. The server stores **only the SHA-256 digest**. The token is **not** an institutional login and has **one purpose**: `POST /v1/sync/backups` under header `Authorization: Device cfsync_…` and the existing CHEMFORGE Android backup JSON format. The destination student is read from the server-side token record. Revocation, expiry, student deletion and institution mismatch reject access. Identical retries are idempotent, conflicts reject atomically, and every mark stays **unverified**.

**This does not turn the Android app into a connected client.** Its manifest still explicitly removes `INTERNET` permission. To submit to the gateway, institutions must use a separate authorised online intermediary. Do not distribute real student identifiers, bearer tokens or backup files over an insecure network. A consent-aware Android sync build and secure provisioning UX remain later projects.

## Safety and architectural boundaries

**For a private, trusted pilot only.** Before real schools: implement SSO/OIDC and MFA, a comprehensive per-teacher authorization audit, TLS and trusted reverse proxy, audit integrity, encrypted server backups, periodic token expiration/rotation, administration safeguards, retention, consent/legal-basis validation, child-data protection, rate limiting, API pagination, threat modelling, and independent security audit. SQLite is single-node storage, not a scalable institutional database. The public HTTP API must not be exposed to the open internet as-is.

Android never uploads automatically in this version; the new device upload API is usable by a separate permitted client only. The server stores no AI-generated explanations or students' free-form answer text. The student-facing app's question bank is still provisional and not a complete expert-approved ZIMSEC syllabus.


## v2.0-alpha: opt-in OIDC staff access token gate

The default **pilot** auth mode is retained for existing synthetic CI and legacy staging. `CHEMFORGE_STAFF_AUTH=oidc` switches staff API authentication entirely to **JWT access-token validation**. In that mode `cfcp_` staff bearer capabilities no longer authenticate, although `cfsync_` **student-device** upload credentials remain deliberately separate. A newly created teacher receives a local actor ID **but no pilot bearer token** and cannot sign in until linked by an operator.

Supported access-token profile is deliberately narrow: RS256 public signatures, explicit `typ: at+jwt` (or `application/at+jwt`), dedicated exact single-value `aud`, HTTPS `iss`, `sub`, `iat`, `nbf`, `exp`, `jti`, `client_id`, duration ≤ 60 minutes, and an `amr` list containing `mfa`. Tokens without an MFA assertion or from unlinked, foreign, or revoked staff are refused. Provider-side policies **must** actually enforce MFA; the server cannot infer genuine MFA from a claim if the issuer is misconfigured. External token `role`, `tenant_id` or `email` never changes the mapped local school role.

1. Use the existing **operator-only** `bootstrap` command and teacher-management API in an isolated pilot to create school and staff records. Note each actor ID.
2. Obtain the authorised provider's exact **HTTPS issuer** and an API-specific **resource audience**. Obtain and independently verify the provider's current public signing keys; store a sanitized **public-only** JWKS JSON file under operator control. Key rotation currently requires updating this file and restarting the API. Never supply token-controlled `jku`/`jwk` URLs or any private signing key.
3. Link an existing, pre-authorised staff account to its immutable issuer `sub` (not email), using **operator access to the SQLite file only**:

   ```bash
   python -m control_plane.cli link-oidc --db ./chemforge-control.sqlite \
     --tenant school-demo --actor-id 'UUID_FROM_STAFF_ROSTER' \
     --issuer 'https://idp.example.org/school' --subject 'PROVIDER_IMMUTABLE_SUBJECT'
   ```

4. Start an isolated server with the exact provider metadata:

   ```bash
   export CHEMFORGE_STAFF_AUTH=oidc
   export CHEMFORGE_OIDC_ISSUER='https://idp.example.org/school'
   export CHEMFORGE_OIDC_AUDIENCE='chemforge-control-api'
   export CHEMFORGE_OIDC_JWKS_FILE='/restricted/jwks-public.json'
   CHEMFORGE_CONTROL_DB=./chemforge-control.sqlite uvicorn control_plane.app:create_app --factory --host 127.0.0.1 --port 8020
   ```

Startup fails when OIDC configuration or keys are missing, duplicated, weak, private, or malformed. In OIDC mode, authorised staff can supply a valid short-lived provider **access** token to the dashboard form (max 12 KB), which holds it in tab memory only. **Do not paste ID tokens.** The API does **not** implement interactive redirect-based OIDC Authorization Code + PKCE, token renewal, IdP discovery, auto-JWKS retrieval, or global logout. Never expose this pilot directly to the internet or to real school data without a formal identity provider integration, TLS hardening, audit and security review.
